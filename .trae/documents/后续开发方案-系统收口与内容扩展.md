# 后续开发方案：系统收口与内容扩展

## Summary
- 目标：在当前“主循环已接通、局外页面已成型”的基础上，完成剩余系统收口，并把开发重心正式切换到黄巾主线内容扩展与战役表达完善。
- 规划原则：
  - 不重复已完成的大改线工作。
  - 优先做“仍影响玩家主体验的缺口”。
  - 继续保持战后轻承接、营地轻整备、图鉴保持图鉴定位。
- 近期版本目标：
  - 让当前可玩主链从“能跑”升级到“稳定、清晰、可扩章”。
  - 为黄巾主线后续章节制作建立统一数据、剧情、页面和验收节奏。

## Current State Analysis

### 已完成并可作为后续基础的部分
- 主流程主链已切到独立战后页：
  - `Scripts/BattleManager.gd` 的 `_end_battle()` 现已组装战后上下文并跳转 `PostBattleReport` / `PostBattleDefeat`。
  - `Scripts/PostBattleReport.gd`、`Scripts/PostBattleRewards.gd`、`Scripts/PostBattleRoute.gd`、`Scripts/PostBattleDefeat.gd` 已承担战后摘要、奖励、去向与失败承接。
- 全局导航契约已形成：
  - `AutoLoad/GameState.gd` 已有 `post_battle_context`、`go_to_level()`、`enter_camp_then_level()`、显示档位设置、教程提示开关与文本节奏保存。
  - `MainMenu`、`SaveSlots`、`LevelSelect`、`CampShop` 已基本改走统一入口。
- 局外页面第一轮统一已完成：
  - `MainMenu`、`SaveSlots`、`CampShop`、`SettingsMenu`、`LevelSelect`、`Barracks` 均已有较统一的古典暗色面板风格。
- 剧情入口规则已简化：
  - `BattleManager.get_dialogue_path_by_id()` 当前优先匹配 `Dialogues/<id>.dialogue`，其次回退 `Dialogues/<id>_start.dialogue`。

### 当前仍然存在的真实缺口
- `BattleManager.gd` 内仍混有“战斗核心职责”和“章节承接职责”：
  - 例如 `play_level_intro()`、`show_victory_dialogue()`、`start_level_id()` 等桥接函数仍堆在战斗主控中。
  - 这会继续放大 `BattleManager` 的职责边界，后续扩章时维护成本会升高。
- `CampShop.gd` 已变成轻整备页，但其内容密度仍偏“功能堆叠”：
  - 当前首屏只汇总伤兵、可募兵、下一战 ID。
  - 缺少更明确的“为何停留、停留后能获得什么、什么时候该离开”的页面引导。
- `SaveSlots.gd` 的信息表达仍停留在“槽位 + 关卡索引”：
  - 这是可用但不够面向玩家，不利于长期主线的读档与分支辨认。
- `LevelSelect.gd` 已有战役卡片，但仍以程序字段为主：
  - 当前显示 `level_id`、敌军数量、敌军军势、是否有剧情前导。
  - 缺少章节分组、通关状态、推荐入口、战线说明等“战役页级”表达。
- `Barracks.gd` 虽已统一主题，但信息结构仍偏开发工具风格：
  - 对玩家而言，标签页、羁绊页、兵种故事区还缺少更清晰的浏览秩序。
- 内容资源层已经出现“扩章前兆”但缺统一节奏：
  - `Dialogues/` 中已存在 `2_1_x` 系列对话资源。
  - 当前未见对应 `Resources/Levels/*.tres` 全量关卡资源与页面侧章节表达同步完成。

### 对当前阶段的判断
- 现在的优先级不再是“再做一轮系统大重构”，而是：
  - 先把页面与导航体验补齐到可长期承载主线内容。
  - 再把黄巾线后续章节按统一模板扩出来。
- 因此下一阶段应拆成两条并行但有先后顺序的工作线：
  - A 线：系统收口与玩家表达升级。
  - B 线：黄巾主线内容扩展。

## Assumptions & Decisions
- 决策 1：不再新增新的全局流程管理器，仍以 `GameState.gd` 为运行态桥接中心。
- 决策 2：`BattleManager.gd` 后续只保留战斗本体与最少量的战斗场景桥接，不继续向其堆积章节导航逻辑。
- 决策 3：`CampShop.gd` 保持轻整备页，不升级为重经营基地。
- 决策 4：`Barracks.gd` 保持图鉴/兵种总览定位，不改造成局内军营中心。
- 决策 5：`SettingsMenu.gd` 当前只继续扩到“玩家常用设置”层，不在近期加入复杂音频总线或键位重绑定。
- 决策 6：内容制作优先服务黄巾主线，`2_1_x` 视为下一批可落地章节候选。
- 假设 1：现有 `RewardPool`、`ShopPool`、`UnitDatabase`、`LevelDatabase` 数据结构足够支撑下一阶段，不优先重构资源格式。
- 假设 2：当前没有可直接调用的本地 `godot` 运行环境，因此验证主要依赖脚本诊断、静态链路检查，以及后续用户在编辑器内补做运行回归。

## Proposed Changes

### Phase 1：导航与职责收口

#### 目标
- 继续减少页面脚本和 `BattleManager.gd` 中分散的“场景跳转 / 剧情桥接”逻辑。
- 把可复用的章节导航职责集中到 `GameState.gd` 或独立桥接工具上。

#### 文件与改动
- `AutoLoad/GameState.gd`
  - 做什么：
    - 提取统一章节入口辅助函数，覆盖：
      - 直接开战
      - 先播剧情再开战
      - 先入营地再开战
      - 读档恢复当前关
    - 统一返回值与失败处理。
  - 为什么：
    - 当前 `MainMenu`、`LevelSelect`、`BattleManager`、对话回调都仍然握有部分入口拼接逻辑。
  - 怎么做：
    - 在现有 `go_to_level()`、`enter_camp_then_level()` 基础上增加更高层包装，例如：
      - `resume_current_level()`
      - `play_level_intro_or_start(level_id)`
      - `route_to_post_battle_destination(mode, context)`
- `Scripts/BattleManager.gd`
  - 做什么：
    - 收缩其桥接职责。
    - 保留战斗场景内确实需要的入口，移除或下放重复导航函数。
  - 为什么：
    - `BattleManager` 继续承担剧情和跳转会让后续章节扩展越来越难维护。
  - 怎么做：
    - 评估并处理：
      - `start_level_id()`
      - `play_level_intro()`
      - `show_victory_dialogue()`
    - 能转移给 `GameState` 或章节桥接层的优先转移。
- `Scripts/MainMenu.gd`
  - 做什么：
    - 进一步消除页面级流程判断。
  - 为什么：
    - 主菜单应只负责入口，不负责恢复逻辑细节。
  - 怎么做：
    - 将 `_on_load_button_pressed()` 中的自动存档恢复细节下放给统一辅助函数。
- `Scripts/SaveSlots.gd`
  - 做什么：
    - 改为调用统一恢复与启动接口，而非自己拼接“取当前索引 -> 启战”。
  - 为什么：
    - 存档页不应成为第二个流程路由中心。

#### 验收标准
- 页面脚本中不再出现多套“根据当前索引拼场景跳转”的重复实现。
- 关键入口只保留一套统一方法。
- 调用失败时有稳定回退路径，不会静默卡死。

### Phase 2：局外页面体验升级

#### 目标
- 让当前局外页从“能用”升级到“玩家一眼能懂、可长期承载主线”。

#### 文件与改动
- `Scripts/CampShop.gd` + `Scenes/CampShop.tscn`
  - 做什么：
    - 强化首屏任务导向。
    - 明确区分：
      - 战前整备摘要
      - 伤兵处理
      - 招募机会
      - 出征按钮
  - 为什么：
    - 当前营地虽然已轻量化，但仍偏系统面板集合，不够“停留 10-20 秒就做完决策”。
  - 怎么做：
    - Header 增加更明确的当前战线名、战前建议语、整备摘要。
    - 招募区显示“本次池特征”或“推荐关注点”。
    - 若当前无需停留，强化“一键出征”的视觉权重。
- `Scripts/SaveSlots.gd` + `Scenes/SaveSlots.tscn`
  - 做什么：
    - 将槽位信息从“关卡索引”升级为“玩家能识别的战役信息”。
  - 为什么：
    - 长期主线下，读档识别成本会持续升高。
  - 怎么做：
    - 读取并显示：
      - 当前关卡名
      - 所属章节或线别
      - 保存类型（自动 / 手动）
      - 可选：军资、玩家库数量、时间戳
- `Scripts/LevelSelect.gd` + `Scenes/LevelSelect.tscn`
  - 做什么：
    - 升级成真正的“战役页”。
  - 为什么：
    - 当前只有关卡卡片，不足以承担未来章节浏览与测试入口。
  - 怎么做：
    - 按章节或路线分组。
    - 显示当前推进位置、未开放/已通关状态。
    - 增加战线简介或推荐说明。
- `Scripts/Barracks.gd` + `Scenes/Barracks.tscn`
  - 做什么：
    - 做第二轮信息架构整理。
  - 为什么：
    - 当前页面在功能上完整，但仍偏“工具页感”。
  - 怎么做：
    - 细化侧栏页签层级文案。
    - 让“已收集 / 全部兵种 / 标签 / 羁绊”之间的切换反馈更明确。
    - 优化右侧详情的首屏信息顺序：
      - 名称
      - 数量/稀有度/类型
      - 占位与标签
      - 故事文本

#### 验收标准
- 四个局外页都具备清晰首屏引导。
- 存档页和选关页不再使用纯开发向字段作为主要信息。
- 新玩家第一次进入也能理解每个页面是做什么的。

### Phase 3：设置系统补全

#### 目标
- 在已完成的 `SettingsMenu` 基础上，补齐近期最值得保留的常用设置项，并保证配置契约清晰。

#### 文件与改动
- `AutoLoad/GameState.gd`
  - 做什么：
    - 在现有显示档位、教程提示、文本节奏之外，补充设置读写契约。
  - 怎么做：
    - 若近期要加新设置，统一继续写入 `user://display_settings.cfg` 或更名为更中性的设置文件路径。
    - 给每个设置提供：
      - getter
      - setter
      - 默认值
      - UI 显示标签
- `Scripts/SettingsMenu.gd` + `Scenes/SettingsMenu.tscn`
  - 做什么：
    - 扩到“近期真正会影响体验”的设置项。
  - 推荐范围：
    - 音量总开关或主音量滑条
    - 战斗提示开关
    - 文本节奏
    - 分辨率
  - 暂不做：
    - 键位重绑定
    - 复杂图形质量分档
    - 多页签高级设置

#### 验收标准
- 所有展示出的设置项都能真正保存并复现。
- 设置逻辑只在 `GameState` 中维护一份真值。

### Phase 4：黄巾主线内容扩展

#### 目标
- 把下一批黄巾主线章节做成“资源可识别、页面可承接、流程可验证”的正式内容批次。

#### 文件与改动
- `Dialogues/*.dialogue`
  - 做什么：
    - 按统一命名与用途整理下一批章节。
  - 怎么做：
    - 入口剧情统一采用：
      - `Dialogues/<level_id>.dialogue`
      - 特殊侧线入口可用 `Dialogues/<level_id>_start.dialogue`
    - 若需要胜利后剧情，则统一约定 `..._victory.dialogue` 是否继续沿用，并补一份页面/脚本调用规则文档。
- `Resources/Levels/*.tres`
  - 做什么：
    - 为现有 `2_1_x` 对话资源补齐对应关卡资源，或反向清理暂不启用的剧情文件。
  - 为什么：
    - 现在对话和关卡存在“预埋资源先于正式关卡”的状态。
  - 怎么做：
    - 以批次为单位推进，例如：
      - 批次 A：先完成 `2_1_1` ~ `2_1_3`
      - 批次 B：再推进 `2_1_4` ~ `2_1_6`
- `Resources/RewardPools/*.tres`、`Resources/ShopPools/*.tres`
  - 做什么：
    - 为新章节关卡补奖励与招募池配置。
  - 为什么：
    - 新章节如果继续使用旧池，会让关卡体验缺少区分度。
- `Scripts/LevelSelect.gd`
  - 做什么：
    - 把新章节同步显示到战役页。
- `Scripts/PostBattleRoute.gd` / `Scripts/CampShop.gd`
  - 做什么：
    - 根据新章节需要补“章节已结束”“下一线未开放”“前往营地整备”等承接文案。

#### 内容制作规则
- 每扩一个新关，必须同时具备：
  - 对应 `LevelConfig`
  - 入口剧情或明确标注“无剧情”
  - 奖励池配置
  - 商店池配置
  - 战后去向验证
- 每个章节批次都应做一次完整静态链路检查：
  - 对话文件命名
  - 关卡资源存在
  - 选关页是否可见
  - 下一关映射是否正确

#### 验收标准
- 至少一批新章节可以从主菜单完整推进到战后页并继续下一关。
- 新章节不依赖临时硬编码映射。

### Phase 5：数据与文档规范固化

#### 目标
- 防止后续内容扩展再次出现“资源有了，但页面、跳转和承接规则不同步”的问题。

#### 文件与改动
- `.trae/documents/`
  - 做什么：
    - 新增一份短规范文档，明确：
      - 关卡命名规则
      - 对话命名规则
      - 战后页链路规则
      - 营地插入规则
      - 新章节验收清单
  - 为什么：
    - 当前很多约定已存在于代码和记忆中，但还没有一份可供持续制作的操作手册。
- 可选新增检查脚本
  - 做什么：
    - 用简单脚本或工具检查 `Dialogues/` 与 `Resources/Levels/` 的同名关系。
  - 为什么：
    - 这类错误最适合自动发现。

#### 验收标准
- 新章节制作不再依赖临场记忆。
- 新人或未来自己回来维护时，能按文档直接补资源。

## Recommended Execution Order
1. Phase 1：导航与职责收口
2. Phase 2：局外页面体验升级
3. Phase 3：设置系统补全
4. Phase 4：黄巾主线内容扩展
5. Phase 5：数据与文档规范固化

## Verification Steps
- 代码诊断：
  - 对每轮改动后的 `.gd` / `.tscn` 使用诊断工具检查错误。
- 静态导航检查：
  - 搜索是否仍有分散的 `change_scene_to_file("res://Scenes/Battle.tscn")` 旧入口。
  - 搜索是否仍有零散的 `skip_intro` 手动控制点。
- 资源链路检查：
  - 核对 `Dialogues/*.dialogue` 与 `Resources/Levels/*.tres` 的同名或约定命名关系。
  - 核对新章节是否具备奖励池、商店池与下一关映射。
- 页面级验收：
  - `MainMenu` 入口清晰。
  - `SaveSlots` 可识别当前战役位置。
  - `CampShop` 能在短停留内完成整备并出征。
  - `LevelSelect` 能清楚表达章节推进。
  - `Barracks` 仍保持图鉴定位。
- 主链路验收：
  - `MainMenu -> SaveSlots/New -> Battle -> PostBattleReport -> PostBattleRewards -> PostBattleRoute`
  - `MainMenu -> Load -> Battle`
  - `LevelSelect -> 剧情前导 -> Battle`
  - `CampShop -> Next Battle`
- 运行验证补充：
  - 若后续本机可用 `godot` 命令，再补一次实际启动与点击流回归，覆盖战斗胜利、失败、读档、营地和选关五条主链。
