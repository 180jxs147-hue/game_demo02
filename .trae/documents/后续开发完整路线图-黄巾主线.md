# 后续开发完整路线图（黄巾主线）

## Summary
- 目标：以现有 Godot 项目为基础，围绕黄巾主线建立“可长期扩展、但战后承接保持轻量”的完整开发路线图。
- 用户决策：
  - 第一优先：主流程闭环。
  - 规划跨度：完整路线图。
  - 范围：纳入代码、UI、美术资源、文案与剧情制作链。
  - 版本目标：长期主线，不只做 Demo。
  - 战后承接：采用“轻承接”，战后页简短清晰，尽快回到下一战或少量整备，不把营地做成当前阶段的重中之重。
  - 内容主线：优先完成黄巾线，不并行推进百年战争主线。
- 总体策略：
  - 先修主循环断点，再补剧情/关卡映射和数据链路，再统一局外页面与资源规范，最后扩充章节内容与长期系统。
  - 保留已存在的独立战后页面，但将其设计为“短链路页面组”，而不是重型经营中枢。

## Current State Analysis

### 已确认的项目基础
- 主入口是 `Scenes/MainMenu.tscn`，由 `project.godot` 指定。
- 核心脚本分布清晰：
  - 全局状态：`AutoLoad/GameState.gd`
  - 战斗主控：`Scripts/BattleManager.gd`
  - 主菜单：`Scripts/MainMenu.gd`
  - 选关：`Scripts/LevelSelect.gd`
  - 营地：`Scripts/CampShop.gd`
  - 图鉴：`Scripts/Barracks.gd`
  - 战后页：`Scripts/PostBattleReport.gd`、`Scripts/PostBattleRewards.gd`、`Scripts/PostBattleRoute.gd`、`Scripts/PostBattleDefeat.gd`
- 数据资源已成体系：
  - 关卡：`Resources/Levels/*.tres`
  - 兵种：`Resources/DataFiles/*.tres`
  - 奖励池：`Resources/RewardPools/*.tres`
  - 商店池：`Resources/ShopPools/*.tres`
  - 标签：`Resources/Tags/*.tres`
- 剧情资源已较丰富，黄巾主线已有 `1_0_x`、`1_1_x`、`1_2_x`、`1_3_1`，并已存在部分 `2_1_x` 对话资源。

### 当前真正跑通的主循环
- 现在实际稳定链路仍以 `Battle` 为中心：
  - `MainMenu -> SaveSlots/Load -> Battle -> Battle 内结算/奖励 -> 下一关或主菜单`
- `CampShop` 不是默认必经页，而是由剧情脚本通过 `enter_camp_before_level(level_id)` 条件插入。
- `LevelSelect` 已能直接播剧情并进战斗，但不在默认新游戏主链上。

### 当前最关键的结构问题
- 战后独立页面已存在，但主流程未彻底切过去：
  - `GameState.gd` 已有 `post_battle_context`、`begin_post_battle_flow()`、`consume_post_battle_context()`
  - `BattleManager._end_battle()` 仍直接 `show_victory_screen()` / `_show_defeat_screen()`
- 对话映射不完整：
  - `BattleManager.get_dialogue_path_by_id()` 仅覆盖到部分 `1_1_4`、`1_2_4`
  - 实际 `Dialogues/` 已存在更多后续章节文件
- 营地链路过度依赖剧情手写跳转：
  - 这适合做特殊演出，不适合作为长期主线的稳定流程基础
- 局外页面风格不统一：
  - `MainMenu`、`SaveSlots`、`MetaShop`、战后页较新
  - `Barracks`、`LevelSelect`、`CampShop` 仍偏旧结构或旧样式
- 卡牌/UI 资源规范尚未收口：
  - `Assets/UI` 已建立基础资源，但卡牌图标、文明纹样、页面面板等仍不完整
- 教程、标签、战斗信息可读性仍处于半完成状态：
  - 有基础框架，但还没有达到长期主线需要的稳定教学与系统表达能力

### 对当前方向的判断
- 项目已经过了“从零到一”的危险阶段，最大问题不是没有系统，而是：
  - 流程断点仍在
  - 老逻辑和新逻辑并存
  - 内容生产与界面统一缺少明确节奏
- 因此后续计划不应再平均用力，而应按照：
  - 主循环闭环
  - 剧情/关卡承接稳定
  - 局外页面统一
  - 内容持续扩张
  的顺序推进。

## Assumptions & Decisions
- 决策 1：黄巾主线是未来数个里程碑的唯一内容主线；百年战争资源只保留为远期预研资产，不进入近期排期。
- 决策 2：战后采用独立页面，但页面链路保持轻量。
  - 胜利推荐链路：`Battle -> PostBattleReport -> PostBattleRewards -> PostBattleRoute -> 下一关/营地/主菜单`
  - 失败推荐链路：`Battle -> PostBattleDefeat -> 重试/读档/主菜单`
- 决策 3：`CampShop` 暂不升级为重型经营中枢，而是保留为“可进入的轻量整备页”。
  - 当前阶段只要求它能承接招募、恢复、少量资源消耗与进入下一战。
  - 不在近期加入复杂基地建设树、长期驻地布局或多页签经营架构。
- 决策 4：`LevelSelect` 中期升级为“战役页”，但不抢占主流程第一优先级。
- 决策 5：完整路线图必须包含制作链规范。
  - 即不仅列代码任务，还要列剧情、关卡、美术 UI、数据资源、验收标准。
- 假设 1：当前 RewardPool / ShopPool 资源结构足够支撑近期扩展，不重构底层数据格式。
- 假设 2：`GameState` 继续承担运行态桥接，不新增新的全局流程管理器。
- 假设 3：现有分辨率双档与 UI 纹理方案继续沿用，不另起一套主题系统。

## Proposed Changes

### Phase 1：打通最小主流程闭环

#### 目标
- 把“已存在但未接通”的战后独立页正式接入。
- 让黄巾主线前几章在不依赖 Battle 内旧 Overlay 的情况下可连续推进。

#### 文件与改动
- `Scripts/BattleManager.gd`
  - 做什么：
    - 改写 `_end_battle(victory: bool)`，不再直接显示旧胜利/失败 Overlay。
    - 战斗结束时统一组装战后上下文，写入 `GameState.begin_post_battle_flow(context)`。
    - 胜利时跳 `Scenes/PostBattleReport.tscn`，失败时跳 `Scenes/PostBattleDefeat.tscn`。
  - 为什么：
    - 这里是主循环断点的根源。
  - 怎么做：
    - 先保留旧 UI 函数作为短期回退源，不立即删除。
    - 新增单一“组装战后数据”函数，集中整理：
      - `level_id`
      - `victory`
      - 我方剩余单位/敌方剩余单位
      - 战斗获得军资
      - 奖励候选
      - 下一关 ID
      - 是否存在下一关
- `AutoLoad/GameState.gd`
  - 做什么：
    - 扩展 `post_battle_context` 的标准结构。
    - 补充读取、消费、清空时的字段约定。
    - 提供统一的“战后去向”辅助函数。
  - 为什么：
    - 当前已有框架，但还不是明确的流程契约。
  - 怎么做：
    - 约定固定键名，避免各页面自己猜字典内容。
    - 增加辅助函数：
      - `get_next_level_id_after(level_id)` 已有，可直接复用
      - 新增类似 `can_continue_after_battle(context)`、`start_level_by_id(id)` 这类导航包装
- `Scripts/PostBattleReport.gd`
  - 做什么：
    - 让其只承担“结果摘要 + 继续按钮”
  - 为什么：
    - 这是轻承接设计的第一页，不应承担复杂决策
  - 怎么做：
    - 默认展示：
      - 胜负
      - 当前关卡名
      - 存活/损失摘要
      - 军资变化
    - 主按钮仅保留“继续”
- `Scripts/PostBattleRewards.gd`
  - 做什么：
    - 承接三选一奖励与确认领取
  - 为什么：
    - 让奖励展示彻底脱离 `Battle`
  - 怎么做：
    - 页面读取 `post_battle_context.reward_options`
    - 选中后调用 `GameState.apply_post_battle_reward(item)`
    - 防止重复领取：领取后在上下文中写入已领取状态，或消费式移除候选
- `Scripts/PostBattleRoute.gd`
  - 做什么：
    - 作为轻量去向页，只给有限选择
  - 为什么：
    - 用户偏好是“轻承接”，因此该页应简短、指向明确
  - 怎么做：
    - 优先按钮：
      - `继续下一关`
      - `进入营地`
      - `返回主菜单`
    - 若无下一关则替换为章节结束文本与回主菜单/营地入口
- `Scripts/PostBattleDefeat.gd`
  - 做什么：
    - 正式替代 Battle 内失败层
  - 为什么：
    - 失败页也要独立于战斗场景
  - 怎么做：
    - 提供：
      - 重试当前关
      - 读取存档
      - 返回主菜单

#### 本阶段细分步骤
1. 定义 `post_battle_context` 字段契约。
2. 在 `BattleManager` 中加入统一上下文组装函数。
3. 将胜利流切到 `PostBattleReport`。
4. 将失败流切到 `PostBattleDefeat`。
5. 将奖励候选迁入 `PostBattleRewards`。
6. 将下一步选择迁入 `PostBattleRoute`。
7. 验证旧 `Battle` 内 Overlay 不再是主流程必要依赖。

#### 验收标准
- 可以完整跑通：
  - `MainMenu -> Battle -> PostBattleReport -> PostBattleRewards -> PostBattleRoute -> Next Battle`
  - `MainMenu -> Battle -> PostBattleDefeat`
- 奖励只发放一次。
- 失败重试不污染手动存档。
- 页面切换后上下文不丢失。

### Phase 2：修复剧情与关卡承接，形成稳定章节推进

#### 目标
- 让黄巾主线的关卡和剧情按 ID 自动承接，不再依赖零散硬编码。

#### 文件与改动
- `Scripts/BattleManager.gd`
  - 做什么：
    - 重构 `get_dialogue_path_by_id(id)` 的实现方式
  - 为什么：
    - 当前手写 `elif` 已无法覆盖现有对话资源数量
  - 怎么做：
    - 近期做法：补齐所有已存在黄巾主线 ID 的映射
    - 推荐中期做法：改为按约定路径自动拼接 `res://Dialogues/<id>.dialogue` 并检查存在性
- `Scripts/LevelSelect.gd`
  - 做什么：
    - 与新的战后/剧情承接规则对齐
  - 为什么：
    - 当前它已实现一套自己的剧情播放逻辑，但未来要和主流程统一
  - 怎么做：
    - 保留 `play_level_intro(id)` 作为桥接接口
    - 统一它与 `BattleManager`、`CampShop` 的 `start_level_id` / `enter_camp_before_level` / `set_shop_pool_for_next_camp` 协议
- `Scripts/CampShop.gd`
  - 做什么：
    - 只保留轻整备逻辑，不承担剧情承接判断
  - 为什么：
    - 剧情和关卡推进规则应集中到全局或统一桥接层，而不是散在营地页
  - 怎么做：
    - 简化 `_on_next_level_pressed()` 中的分支优先级
    - 尽可能改为读取统一上下文或统一导航函数
- `Dialogues/*.dialogue`
  - 做什么：
    - 整理黄巾主线中“战前剧情 / 战后过渡 / 插入营地”的使用规则
  - 为什么：
    - 当前部分对话直接开战，部分先入营地，规则不一致
  - 怎么做：
    - 约定：
      - 战前剧情结束常规进入战斗
      - 特殊整备关前才调用 `enter_camp_before_level`
      - 战后不在对话里承担奖励或结算逻辑
- `Resources/Levels/*.tres`
  - 做什么：
    - 逐关核查 `level_id` 与剧情文件命名是否一致
  - 为什么：
    - 后续自动承接依赖命名一致性

#### 本阶段细分步骤
1. 盘点所有黄巾主线 `level_id`、`dialogue id`、关卡资源。
2. 统一命名规范，形成一一对应表。
3. 改造对话路径解析方式。
4. 清理“当前关卡重复播放 intro”与“营地回战斗再播一次”的问题。
5. 把剧情跳转规则写成固定约定，供后续新章节复用。

#### 验收标准
- 黄巾主线现有章节均可按 ID 正确找到剧情。
- 同一段剧情不会重复播放。
- 进入营地、跳过营地、直接下一战三种路径都不出现死循环或错关。

#### 目标
- 让 `Battle.tscn` 重新聚焦为战斗场景，而不是结果 UI 聚合器。

#### 文件与改动

  - 做什么：
    - 标记并移除不再使用的旧结算 UI 流程
  - 为什么：
    - 新旧流程长期并存会继续制造回归问题
  - 怎么做：
    - 在 Phase 1 稳定后，逐步删除或废弃：
      - `show_victory_screen()`
      - `_show_defeat_screen()`
      - `_show_rewards()` 相关旧界面节点依赖
      - “下一关按钮/重试按钮/菜单按钮”旧路径
- `Scenes/Battle.tscn`
  - 做什么：
    - 清理专属于旧战后结算的节点
  - 为什么：
    - 缩小场景体积与耦合
- `Scripts/BattleLogUI.gd`
  - 做什么：
    - 补足最必要的滚动/尾部对齐行为
  - 为什么：
    - 战斗场景回归专注后，日志与 HUD 的清晰度更重要

#### 验收标准
- `Battle` 结束后不再依赖旧 Overlay 节点。
- 旧代码删除后不影响主流程。
- 战斗场景层级更简洁，后续战斗功能修改风险下降。

### Phase 4：把 CampShop 调整为轻量整备页，而不是重经营页

#### 目标

    - 以轻量整备为目标调整布局
  - 为什么：

      - 招募
      - 医疗/恢复
      - 下一战准备
    - 不在当前阶段扩展复杂基建树
- `Scripts/CampShop.gd`

  - 怎么做：

    - 明确哪些标签只做展示，哪些标签已进入实际战斗逻辑
  - 为什么：
    - 长期主线会持续新增兵种，不先明确标签语义会快速失控
- `Resources/Tags/*.tres`
  - 做什么：
    - 完善标签描述、分类和图鉴展示文本
- `Scripts/BattleManager.gd` / `Scripts/Tooltip.gd` / `Scripts/CardSlot.gd`
  - 做什么：
    - 强化战斗信息提示与卡牌可读性

#### 内容与文案任务
- 为黄巾主线核心标签补文案：
  - 兵种定位说明
  - 标签机制说明
  - 克制关系提示
- 为新手流程补“首次出现提示”

#### 验收标准
- 新玩家能通过教程与图鉴理解主线前几章机制。
- 常用标签在战斗、图鉴、卡牌处的描述一致。

### Phase 7：进入黄巾主线持续内容生产

#### 目标
- 在流程稳定后，持续扩充黄巾主线章节、兵种、奖励和演出。

#### 内容生产链
- 剧情：
  - `Dialogues/`
  - 为每个新关卡补：
    - 战前剧情
    - 可选战后短过场
    - 关键分支对话
- 关卡：
  - `Resources/Levels/*.tres`
  - 保持关卡命名、剧情命名、奖励/商店池命名一致
- 奖励：
  - `Resources/RewardPools/*.tres`
  - 按章节分层，避免随机池污染成长节奏
- 商店：
  - `Resources/ShopPools/*.tres`
  - 让招募池与章节敌我阵营相呼应
- 图鉴与兵种：
  - `Resources/DataFiles/*.tres`
  - `Resources/ImageFiles/`
  - `Assets/UI/Cards/`

#### 生产顺序建议
1. 先补全黄巾主线现有章节缺失的战前/战后衔接。

3. 最后扩展到第二章以后新增内容。

#### 验收标准
- 新增章节不需要额外发明流程接口，直接套现有主链即可。
- 每一章都具备：剧情、关卡、奖励、图鉴、商店、基础教程支撑。
